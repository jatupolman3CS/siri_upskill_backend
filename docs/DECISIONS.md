| **D-23** | **Notification delivery — Transactional Outbox → Kafka → idempotent consumers · Redis เป็น duplicate-guard / send-throttle / unread-count cache · opt-in ด้วย `Notification:Delivery:Transport`** (2026-10-09) | เจ้าของโปรเจ็คสั่ง "เพิ่มเรื่อง notification ไปใช้ kafka + redis ด้วย best solution" — ตัดสินใจ: (1) **DB ยังเป็น source of truth และจุดเขียน atomic**: outbox เดิม (`NOTIFY.EMAIL_OUTBOX`, `NOTIFY.NOTIFICATIONS`) ที่ caller commit ใน tx เดียวกับ business write — `IEmailOutbox`/`IUserNotificationOutbox` **ไม่เปลี่ยน** จึงไม่มี caller ใดต้องแก้; ห้าม publish Kafka ตรงจาก request (dual write); **relay (อีเมล)** claim ด้วย tx สั้น (`FOR UPDATE SKIP LOCKED` → mark `Queued` → **commit**) แล้ว publish (idempotent producer, acks=all) โดยไม่ถือล็อก DB; broker ไม่ ack = คืนแถวเป็นสถานะเดิม (compare-and-swap) ⇒ at-least-once, แถว `Queued` ค้างเกิน 15 นาทีถูก claim ใหม่ **เฉพาะเมื่อ consumer ไม่ได้ทำ record ใดเสร็จเลยในช่วงนั้น** (heartbeat ใน Redis — แยก "backlog ยาวที่ต่อคิวอยู่" ออกจาก "record หาย" ไม่ให้ publish หางคิวซ้ำทุกรอบ) · release ของแถวที่ broker ไม่รับล็อกแถวระหว่างตรวจ+เขียน (ไม่ทับผลที่ consumer เพิ่ง commit) — **ไม่ publish ใน tx เดียวกับล็อก** เพราะ consumer อาจอ่านแถวก่อน relay commit แล้วทับสถานะ (บั๊กที่ e2e test กับ Kafka จริงเจอ) · in-app: ถือล็อกระหว่าง produce ได้ (consumer ไม่อ่านแถว) แล้ว mark `PublishedAtUtc` (2) **claim check**: record มีแค่ `messageId` — body (มีลิงก์ reset password) / subject / อีเมลไม่เข้า broker, key = message id (ไม่ใช้อีเมล/hash ของอีเมล เพราะ hash เดาย้อนได้จากรายชื่อ — ผู้อ่าน topic ยืนยันไม่ได้ว่าอีเมลไหนอยู่ในสตรีม) และ DLQ `reason` เป็นชื่อชนิด exception เท่านั้น (3) **consumer idempotent**: สถานะแถวใน DB + Redis claim (`SET NX`, 5 นาที) → SMTP → จด "delivered" ใน Redis **ก่อน** `SaveChanges`; Redis ล่ม = fail-open (ยึดสถานะแถว) (4) **retry state อยู่ใน DB** (backoff 1/2/4/8 นาที สูงสุด 5 ครั้งตาม `EMAIL_OUTBOX_MESSAGE`) แล้ว relay publish ใหม่เมื่อถึงเวลา; หมดสิทธิ์ = แถว `Failed` ไม่มี retry = dead letter (metric + log Error) ส่วน DLQ topic ไว้ record ที่ประมวลผลไม่ได้เลย (poison / consumer ยอมแพ้) (5) **Redis 3 บทบาท ไม่ใช่ที่เก็บของที่ห้ามหาย**: delivery guard, งบส่งต่อนาทีร่วมทุก consumer (`MaxEmailsPerMinute`), cache จำนวนยังไม่อ่าน (`GET /api/notifications/unread-count`) invalidate ด้วย event in-app (6) **opt-in + ย้อนกลับได้**: default `Transport=Database` = Hangfire job เดิม; เปลี่ยนเป็น `Kafka` job จะ stand down และสลับกลับได้ (job adopt แถว `Queued` ที่ค้าง); สองทางเรียก `EmailDeliveryHandler.DeliverAsync` ตัวเดียวและแชร์ Redis claim ⇒ ช่วงเปลี่ยนผ่านไม่ส่งซ้ำ (7) **รันที่เดียวกับ Hangfire server** (API เมื่อ `ServerInApi`, Workers เสมอ) (8) **namespace ด้วย `Kafka:TopicPrefix`** (+ `ReplicationFactor`) ⇒ หลาย environment ใช้ cluster เดียวกันได้; production guard ปฏิเสธ `Plaintext`/`SaslPlaintext` นอกจาก `Kafka:AllowPlaintext=true` — ไม่เลือก: CDC/Debezium (หนักเกินสำหรับ VPS เดียว), Redis Streams เป็น backbone (ไม่มี retention/replay ระดับที่ต้องการ). **ต้นทุน/ข้อควรรู้ของเจ้าของ**: Kafka เป็น stateful service ตัวใหม่ (JVM ~1 GB RAM) บน VPS ที่ใช้ร่วมกัน — การเปิดใช้คือการตัดสินใจเรื่อง capacity ของเจ้าของ; ### ✅ Q8 — Anti-piracy bar = **คง MediaCage Basic แล้วแก้ acceptance ให้ตรงความจริง + ชดเชยด้วย forensic watermark** (ตัดสิน 2026-08-25)

> **ใครตัดสิน:** เจ้าของโปรเจ็คสั่งให้ Claude Code ตัดสินแทน (2026-08-25) · **เลือกทางที่ 2** จาก 3 ทางที่เสนอไว้เดิม

**ปัญหาเดิม:** `TASKS.md` P2-31 + exit criteria ของ P2 เขียนว่า "IDM / extension / `yt-dlp` / copy manifest URL / devtools **ต้องล้มเหลวทุกทาง**" แต่ Q1 เลือก **MediaCage Basic** ซึ่งเป็น clear-key encryption ไม่ใช่ Widevine/FairPlay/PlayReady — กุญแจถอดรหัสถึงมือ client ในรูปแบบที่ดึงออกได้ด้วยเครื่องมือมาตรฐาน bar เดิมจึงเป็นเป้าที่ทำไม่ได้จริงไม่ว่าจะเขียนโค้ดดีแค่ไหน

**สิ่งที่ตัดสิน:**

1. **ไม่อัปเกรด tier ตอนนี้** — เก็บงบไว้ก่อน · เหตุผล: (ก) ภัยจริงของ marketplace คอร์สไทยส่วนใหญ่คือการแชร์บัญชีและอัดจอแบบง่าย ๆ ซึ่ง MediaCage Basic + concurrent-session limit (SE-03, ทำแล้วตั้งแต่ P0-17) + signed URL อายุสั้นรับมือได้ (ข) DRM จริงต้องทำ FairPlay certificate กับ Apple เพิ่ม เป็นงานและเวลาที่ไม่คุ้มก่อน launch (ค) ถ้าถึงจุดที่คุ้มค่อยอัปเกรดได้ทีหลัง — โค้ดอยู่หลัง `IVideoProvider` อยู่แล้ว ไม่ใช่ทางตัน
2. **เปลี่ยนกลยุทธ์จาก "กันไม่ให้ดึง" เป็น "ดึงได้แต่รู้ว่าใครปล่อย"** — จุดที่ต้องแข็งจริงคือ:
   - `P2-22` **dynamic watermark** ที่ระบุตัวผู้ดูได้ (ชื่อ+อีเมล+timestamp, payload มาจาก server เท่านั้น) — กลายเป็นของบังคับ ไม่ใช่ของแถม เพราะเป็นกลไกไล่ต้นตอหลัก
   - `P2-04` signed URL อายุ 2–5 นาที + entitlement check ทุกครั้ง (ทำแล้ว)
   - `P2-06` anomaly detection (ดูเกินปกติ/หลาย IP) — เลื่อนความสำคัญขึ้นจาก "ทำก็ดี" เป็น "ต้องมีก่อน launch" เพราะเป็นเซนเซอร์ตัวเดียวที่จับการปล่อยเนื้อหาได้
   - `P0-17` concurrent-session limit (ทำแล้ว) — คือด่านที่กันการแชร์บัญชีจริง ๆ
3. **แก้ acceptance ของ P2-31 ให้เป็นเป้าที่วัดได้จริง** (แทนข้อความ "ต้องล้มเหลวทุกทาง"):
   - ✅ ต้องกันได้: ดาวน์โหลดตรงจาก URL ในแท็บ network, copy manifest URL ไปเปิดเครื่องอื่น/หลังหมดอายุ, IDM และ video-downloader extension ยอดนิยม, การเข้าถึงโดยไม่มี enrollment
   - ⬜ ยอมรับว่าทำไม่ได้: ผู้โจมตีที่ดึง clear-key ออกจาก player ด้วยเครื่องมือเฉพาะทาง (เช่น `yt-dlp` + key extraction) และการอัดหน้าจอ
   - 📋 ต้องพิสูจน์เพิ่ม: วิดีโอที่หลุดออกไปต้อง **ระบุตัวผู้ดูต้นทางได้จาก watermark** (ทดสอบจริง: อัดหน้าจอ 1 คลิปแล้วอ่านย้อนว่าเป็นบัญชีไหน)
   - **ห้ามลด scope ของเทสต์เพื่อให้ผ่าน** — ถ้าเจอช่องที่อยู่ในกลุ่ม "ต้องกันได้" แล้วกันไม่ได้ ต้องรายงานตรง ๆ ไม่ใช่ย้ายมันไปกลุ่ม "ยอมรับ"
4. **เงื่อนไขที่จะกลับมาทบทวน (revisit trigger)** — ให้ยกกลับมาพิจารณาอัปเกรด tier เมื่อเข้าข้อใดข้อหนึ่ง:
   - พบการปล่อยคอร์สจริงจาก watermark forensics มากกว่า 1 ครั้ง
   - มีคอร์สราคาสูง (> ฿10,000) หรือลูกค้าองค์กร (P9) ที่ระบุ DRM เป็นเงื่อนไขในสัญญา
   - Bunny ออก tier ที่ราคาต่างไปอย่างมีนัยสำคัญ

**ผลต่อ P2-05 (DRM license proxy):** MediaCage Basic ไม่มี license server แบบ DRMจริงให้ proxy — งานของ P2-05 จึงเปลี่ยนรูปเป็น "**key delivery ต้องผ่าน endpoint ของเราที่ตรวจ entitlement ซ้ำ ห้ามให้ client คุยกับ Bunny ตรง**" ตามเจตนาเดิมของ `security.md` · ถ้าตรวจแล้วพบว่า Bunny ไม่เปิดให้ทำแบบนั้นเลยในระดับ Basic ให้รายงานกลับมาก่อน อย่าเงียบ ๆ ปล่อยให้ client คุยตรง

### ✅ Q10 — Google account model สำหรับสร้าง Meet/Calendar = **ทางเลือก B: ผู้สอนเชื่อม Google เอง** (ตัดสิน 2026-09-16)

**ผลต่อสถาปัตยกรรม (แก้จาก draft เดิมที่สมมติทาง A):**
- ต้องมีหน้า/flow "เชื่อมต่อ Google Calendar" ใน Instructor Studio — OAuth consent (scope `https://www.googleapis.com/auth/calendar.events` ขั้นต่ำที่ Meet API ต้องการ — ยืนยัน scope ที่แท้จริงตอนเขียน contract) → เก็บ **refresh token เข้ารหัสผ่าน `Siri.SharedKernel.ISensitiveDataProtector`** (มีโครงอยู่แล้วจาก Payout's bank-account encryption fix) ลงเอนทิตีใหม่ `InstructorGoogleAccount` (1:1 ต่อ `InstructorProfile`)
- `ICalendarProvider` (Q10 เดิมออกแบบเป็น impersonate service account ตัวเดียว) **ต้องเปลี่ยนเป็นรับ credential ต่อ call** — resolve จาก refresh token ของผู้สอนเจ้าของคอร์สนั้น ไม่ใช่ credential กลางตัวเดียวอีกต่อไป
- Live/Hybrid course สร้าง session ที่มี Meet จริงได้ก็ต่อเมื่อผู้สอนเชื่อม Google แล้วเท่านั้น — ยังไม่เชื่อม = ใช้ **`SESSION_MEETINGS.PROVIDER = Manual`** (degraded mode เดิมที่ออกแบบไว้แล้ว) ผู้สอนวางลิงก์เอง
- **ความเสี่ยงใหม่ที่ต้องรับทราบก่อนเริ่ม P11-03:**
  1. Google OAuth app ที่ขอ scope `calendar` (sensitive scope) ต้องผ่าน **verification ของ Google ก่อนใช้กับผู้ใช้ทั่วไป — ใช้เวลาเป็นสัปดาห์** ระหว่างรอ ใช้โหมด "Testing" ได้กับ test user ไม่เกิน 100 คน (พอสำหรับ dev/beta) — **เจ้าของโปรเจ็คควรเริ่มขั้นตอนนี้ทันที** (สร้าง OAuth consent screen ใน Google Cloud Console, submit verification) เพราะเป็น critical path ที่ยาวกว่างานเขียนโค้ดเอง
  2. ผู้สอนถอนสิทธิ์ (revoke) เมื่อไหร่ก็ได้ = token ใช้ไม่ได้ทันที ห้องที่ตั้งไว้ล่วงหน้าจะ sync ไม่ได้อีก — ต้องมี job ตรวจจับ token invalid (401 จาก Google) แล้วแจ้งเตือนผู้สอนให้เชื่อมใหม่ + fallback session ที่ได้รับผลกระทบเป็น `Manual`
  3. เพดานผู้เข้าร่วม/ระยะเวลาประชุมเป็นไปตาม**แผน Google ของผู้สอนแต่ละคนเอง** (Gmail ฟรี ~100 คน/60 นาทีสำหรับกลุ่ม, ถ้าผู้สอนมี Workspace ส่วนตัวจะสูงกว่า) — แพลตฟอร์มควบคุมจากส่วนกลางไม่ได้อีกต่อไป ต้องแจ้งเตือนผู้สอนเรื่องนี้ในหน้า builder ตอนตั้งตารางสอน
- ทางเลือก A (Workspace กลาง) **ตกไป** ไม่ต้องซื้อ Google Workspace ให้แพลตฟอร์ม · ทางเลือก C (ผู้สอนวางลิงก์เอง) ยังคงเป็น degraded fallback (`Manual`) เหมือนเดิม

### Q11 — ช่องทางเชิญเข้าปฏิทิน: ICS ของเราเอง vs Google attendee = **ยืนยันตาม default** (ตัดสิน 2026-09-16)
**ICS ผ่าน `EmailOutbox` เป็น baseline ทุกคน** (UID = session id, SEQUENCE เพิ่มเมื่อแก้, METHOD:CANCEL เมื่อยกเลิก — ใช้ได้ทั้ง Gmail/Outlook/Apple) + **Google attendee sync เป็น opt-in ต่อคอร์ส** ปิดอัตโนมัติเมื่อผู้เรียนเกิน `Live:GoogleAttendeeCap` (default 150) · เหตุผล: เพดาน 200 guest/event + quota อีเมลของ Google + PDPA (attendee list ทำให้ผู้เรียนเห็นอีเมลกันเอง) — ไม่มีอะไรเปลี่ยนจาก draft เดิม (Q10=B ไม่กระทบ Q11 เพราะ attendee sync ยังเรียกผ่าน `ICalendarProvider` เหมือนเดิม แค่ credential ที่ใช้เปลี่ยนที่มา)

### Q12 — AI: ผู้ให้บริการ, งบ, และ opt-in = **ยังไม่เปิดตอนนี้ — เลื่อน P12 ทั้งเฟส** (ตัดสิน 2026-09-16)
เจ้าของโปรเจ็คเลือก**ไม่เปิดใช้ AI ในรอบนี้** — **P12 (AI Study: transcript/chapter/summary/watch-plan/marketing copy) ทั้งเฟสเลื่อนออกไปก่อน** ไม่ผูกกับ P11 เลย (P11 ไม่มี dependency ไปทาง P12) · ไม่เพิ่ม dependency `Anthropic` SDK ในรอบนี้ · ไม่เปิด Bunny Transcribe AI · `Course.AiEnrichmentEnabled` (ถ้าถูกสร้างจาก P11 migration ใด ๆ) คง default `false` ตลอดไปจนกว่าจะมีคำสั่งเปิดใหม่ — revisit ได้ทุกเมื่อโดยไม่กระทบ P11 ที่ทำไปแล้ว (ออกแบบแยกโมดูล `Siri.Integrations.Ai` ไว้ต่างหากอยู่แล้วตาม `HYBRID_LIVE.md` §3)

### ✅ Q13 — นโยบายคอร์สสอนสด (ตัดสิน 2026-09-16, ทั้ง 5 ข้อ)
1. **ปิดรับสมัครเมื่อไหร่** = **ผู้สอนตั้งวันปิดรับสมัครเองต่อคอร์ส** (ไม่ใช่ default เดิม "ขายได้จนจบคาบสุดท้าย") — ต้องมีฟิลด์ใหม่ `Course.EnrollmentDeadlineUtc` (nullable, null = ไม่ปิดรับสมัคร) ตั้งได้จาก builder · enforce ที่จุดสร้าง Order: ปฏิเสธคำสั่งซื้อคอร์สนี้ถ้า `now > EnrollmentDeadlineUtc` (409) — คนที่ enroll ไปแล้วก่อนหน้าไม่กระทบ
2. **เพดานที่นั่ง** = **ผู้สอนตั้ง `MaxSeats` เองต่อคอร์ส** (ไม่ใช่ default เดิม "ไม่ hard cap") — `Course.MaxSeats` (nullable int, null = ไม่จำกัด) · enforce แบบ **atomic ที่ระดับ SQL** ตอนสร้าง order/enrollment (ห้ามอ่านนับใน memory แล้วค่อยเขียนตาม `database.md` — pattern เดียวกับที่ร่างไว้สำหรับ `corporate.OrgCourseLicenses`'s seat count ใน P9)
3. **`AccessDurationDays` นับจากไหน** = **นับจาก `StartsAtUtc` ของ live session แรกสุดที่ตั้งไว้** (ไม่ใช่ default เดิม "วันซื้อ") สำหรับคอร์ส Live/Hybrid เท่านั้น (คอร์ส OnDemand ยังนับจากวันซื้อเหมือนเดิม ไม่เปลี่ยน) — **edge case ที่ต้องตัดสินใจไว้ล่วงหน้า**: ถ้ายังไม่มี session ไหนถูกตั้งเลยตอนที่มีคนซื้อ (เช่น ผู้สอนเปิดขายไว้ก่อนตั้งตาราง) ให้ fallback เป็นวันซื้อแทน (ยอมรับเป็น edge case ที่หายาก ไม่ใช่ dead-end — เขียนกำกับไว้ในโค้ดชัดเจนตอน implement)
4. **Refund หลังเข้าเรียนสดแล้ว** = **ห้าม refund อัตโนมัติทันทีที่ผู้เรียนเข้าคาบสดไปแล้วอย่างน้อย 1 คาบ** (ไม่ใช่ default เดิม "ใช้ policy เดิมทั้งหมด ให้ admin ตัดสิน") — เช็คจาก `LIVE.SESSION_JOIN_LOGS` ว่ามี row ของ enrollment/คอร์สนี้หรือไม่ ถ้ามี → `RefundService.RequestAsync` ปฏิเสธทันทีที่ระบบ (409, ไม่ต้องเข้าคิว admin เลย) — เหตุผล refund อื่นที่ไม่เกี่ยวกับการเข้าเรียนสด (เช่น เนื้อหาไม่ตรงโฆษณา, เทคนิคผิดพลาดฝั่งแพลตฟอร์ม) ยังใช้กระบวนการเดิม (admin approve/reject) เหมือนเดิมทุกอย่าง — งานนี้เป็นการเพิ่ม hard-block เฉพาะกรณีเดียว ไม่ใช่เปลี่ยน flow refund ทั้งหมด
5. **Recording อัตโนมัติจาก Google Meet → Drive** = **ยืนยันตาม default: ไม่ทำใน v1** (ต้อง Drive scope + ดึงไฟล์ผ่าน VPS ขัด D-15) ผู้สอนดาวน์โหลดเองแล้วอัปผ่าน TUS เหมือนเดิม
